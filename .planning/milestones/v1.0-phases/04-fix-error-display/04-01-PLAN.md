Fix `handleRetry` in `src/components/chat/MessageList.jsx` (~line 32-47) to use the new `CLEAR_ERROR_MESSAGE` action instead of dispatching `SET_ERROR` with null.

**Key changes:**
1. Dispatch `CLEAR_ERROR_MESSAGE` instead of `SET_ERROR` with null — this removes the error bubble from `state.messages` AND clears `state.error`
2. Filter `!m.isError` when building `apiMessages` — prevents error message content ("Oops, something went wrong...") from leaking into the API conversation history
3. The `sendMessage` call remains unchanged — it dispatches `START_BOT_MESSAGE` with a fresh UUID, creating a clean new bot message for streaming

Replace the entire `handleRetry` function:
```jsx
// Retry handler: resend the last user message
const handleRetry = () => {
  // Find the last user message
  const lastUserMsg = [...state.messages]
    .reverse()
    .find((m) => m.role === 'user');
  if (!lastUserMsg) return;

  // Clear error state
  dispatch({ type: 'SET_ERROR', payload: null });

  // Rebuild API messages up to and including the last user message
  const apiMessages = state.messages.filter(
    (m) => m.role === 'user' || m.role === 'assistant'
  );
  sendMessage(apiMessages);
};
```

With:
```jsx
// Retry handler: remove error bubble and resend the last user message
const handleRetry = () => {
  const lastUserMsg = [...state.messages]
    .reverse()
    .find((m) => m.role === 'user');
  if (!lastUserMsg) return;

  // Build API messages BEFORE clearing — exclude error bubbles from context
  const apiMessages = state.messages.filter(
    (m) => (m.role === 'user' || m.role === 'assistant') && !m.isError
  );

  // Remove error bubble from messages and clear state.error
  dispatch({ type: 'CLEAR_ERROR_MESSAGE' });

  // sendMessage creates a fresh bot message via START_BOT_MESSAGE
  sendMessage(apiMessages);
};
```

**Important:** `apiMessages` MUST be built before dispatching `CLEAR_ERROR_MESSAGE`. The dispatch is synchronous in React's batching model but the reference to `state.messages` is captured at render time — building the filtered list first is cleaner and avoids any ambiguity about state timing.
